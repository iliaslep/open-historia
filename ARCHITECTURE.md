## Проблемы, определяющие план

1. LLM предлагает события и численные изменения, затем существующие валидаторы
   и `applyEventImpactsToWorld` применяют их. Это не заменяет законов экономики,
   ратификации договоров и ресурсных ограничений. Формальная JSON-схема недостаточна.
2. `countryStats` хранится, но исходные значения могут быть AI-оценками. Нельзя
   преобразовать их в «исторические факты» без происхождения и единиц.
3. `maybeSendIdleDiplomacy` использует `Math.random`, есть процессы вне продвижения
   даты. Для нового режима нужны управляемая случайность и запрет значимых
   изменений мира во время паузы; косметическое движение не равно ходу.
4. Нормализация мира перечисляет поля явно. Просто добавить `world.simulation`
   недостаточно: нужны round-trip тесты всех read/write/export/import путей.
5. Сохранения распределены по assets; атомарная запись отдельного файла не
   доказывает атомарность полного хода. Нужны journal/revision, восстановление
   и проверка частичных отказов до включения расчётного режима.
6. Рабочая сборка/тесты не доказывают качество карты в браузере. Визуальная
   проверка и длинная партия пока не выполнены.

## Целевая схема (движок ещё не реализован)

```text
Русские панели / свободный текст
          |                       LLM-провайдер
          |                      -> предложение команды
          v                                |
Проверка схемы, полномочий, ресурсов, видимости и времени
          |
Чистый движок: advance(state, command, rules) -> nextState + events + receipts
          |
Адаптер существующего состояния и сохранений / единая фиксация ревизии
          |
Существующие API -> карта, панели, память, экспорт
```

Новые общие чистые модули размещаются в `server/simulation/`: существующая
упаковка поставляет сервер без `src/`, что проверяет `server/serverImports.test.js`.
Клиент импортирует их так же, как другие общие серверные helpers. Модули не
зависят от React, fetch, localStorage или системных часов. Контракты описаны
JSDoc с `@ts-check` и проверяются TypeScript без нового runtime/loader; так
сохраняется совместимость с существующим JS-стеком и Node test runner.
Выделять модули по мере реализации: state/commands, time/PRNG, economy,
diplomacy, politics, intelligence, military, characters, autonomousAI.
Не создавать заранее десятки пустых модулей.

Предполагаемый заголовок сохранения: `schemaVersion`, `rulesVersion`, `revision`,
`scenarioId`, `date`, `rngState`. Типы стран, договоров, действий и источников
получают явные единицы и ID. `rngState` содержит текущее состояние PRNG, не только
первоначальный seed. Миграции идут последовательно и не перезаписывают оригинал
до успешной валидации. Снимок старой партии остаётся восстановимым.

Первый реализованный контракт — `world.simulation` в `server/simulation/state.js`:
`schemaVersion: 1`, `rulesVersion: 1`, `scenarioId`, `date`, `revision`,
`rng: { algorithm: 'mulberry32-v1', seed, state, draws }`.
Версия 1 заголовка принимает канонические даты нашей эры 0001–9999;
старые сценарии до н. э. остаются в прежнем режиме и не изменяются.
Календарная арифметика используется через общий gameDates; её реализация
перенесена в поставляемый `server/` без изменений, клиентский импорт сохранён.
Отсутствие поля сохраняет legacy-формат; явное создание заголовка не включает
новый исполняющий движок и не меняет существующий UI. При чистом календарном
шаге согласование с `game.gameDate` проверяет `advanceSimulationClock`;
обычная запись header через прежний API сама по себе не выполняет игровой ход.
Валидатор отклоняет неизвестные версии/поля, повреждённые значения и несовместимый
PRNG; миграций между расчётными версиями пока нет, первая поддерживаемая — 1.
Проверка не «лечит» данные значениями по умолчанию и не создаёт seed автоматически.

`drawRandom` — чистая функция: возвращает значение [0, 1) и новый checkpoint,
не меняя вход. Используется Mulberry32 с фиксированной арифметикой uint32;
проверяется согласованность seed/state/draws и переполнение счётчика.
Нормализатор клиента сохраняет отдельную копию checkpoint; серверный и веб-backend
проверяют входящие runtime-записи и импорты до изменения данных партии.
Проверка вложенных rollback snapshots, общая миграция всех assets и транзакция
полного игрового хода остаются отдельной работой, не следуют из этого контракта.

`server/simulation/time.js` реализует чистые `advanceSimulationDay`,
`advanceSimulation` (day/week/month) и `advanceSimulationClock` (пара game/world).
Месяц — тот же день следующего календарного месяца с ограничением последним
днём, например 2016-01-31 → 2016-02-29. Все интервалы проходят общий дневной шаг.
`revision` считает обработанные дни, а не запросы или записи сохранения:
неделя эквивалентна семи дневным шагам. На этом участке дни ещё не выполняют
экономику/NPC и не расходуют RNG; checkpoint сохраняется.

Адаптер отклоняет legacy-партию и расхождение двух дат, возвращает независимые
копии game/world с одинаковой новой датой и числом прошедших дней. Он не меняет
legacy round, не пишет файлы/IndexedDB, не включает новый режим UI и не является
транзакцией сохранения. Переполнение revision и выход за диапазон дат header v1
отклоняются без изменения входного состояния. Локальная запись результата
с контролем revision описана ниже; веб-адаптер, UI и решения NPC следуют отдельно.

### Локальная фиксация календарного шага

`POST /api/games/:gameId/simulation/advance` принимает только
`{ "step": "day" | "week" | "month", "expectedRevision": integer }`.
`advanceGameClock` в libraryStore обращается к конкретной партии, независимо
от выбранной в интерфейсе. Клиент не присылает замену мира: результат вычисляет
сервер. Ответ содержит gameId, game, world и days. Устаревшая revision даёт 409,
некорректная команда/legacy-партия — 400, отсутствующая партия — 404,
неожиданная ошибка хранения — 500. UI пока не вызывает эту операцию.

`server/simulation/clockStore.js` синхронно выполняет сравнение revision и
фиксацию в одном процессе сервера. До изменения файлов публикуется
`.simulation-clock-journal.json`: версия envelope, сериализованный результат
и SHA-256 payload. Он содержит game, world и метаданные партии; updatedAt
обновляется вместе с ними, чтобы восстановленный ход менял cacheToken.
Затем три файла по очереди заменяются через временные файлы, fsync и rename;
после завершения journal удаляется. На поддерживаемых платформах синхронизируется
также каталог. Windows использует atomic rename без directory fsync.

Опубликованный journal означает намерение завершить ход. После прерывания
восстановление повторно записывает весь результат и удаляет journal; повторение
восстановления безопасно. Оно встроено в чтение/запись верхнеуровневых JSON-файлов
партии и getGameDetails. Ошибка разбора, неподдерживаемая версия или несовпадение
SHA-256 не приводят к сбросу данных: journal остаётся, чтение пары завершается
ошибкой до её выдачи. Экспорт после успешного восстановления видит одну дату.

Сбой после публикации journal может вернуть 500, хотя ход уже зафиксирован либо
будет завершён восстановлением. Клиент должен перечитать указанную партию и её
revision; повтор исходного запроса получает 409 и не выполняет ход дважды.
Это проверено завершением дочернего процесса после каждого из четырёх rename.
Отдельно проверены отказ до публикации journal и восстановление штатным чтением
libraryStore в новом процессе.

Граница гарантии — календарная операция локального сервера, один процесс на
каталог данных. Межпроцессной блокировки нет. Старые raw PUT/update API не
получили CAS; новый UI должен использовать специальную операцию, а переключение
режима должно исключить конкурирующие legacy-писатели. Веб/Android IndexedDB,
NPC, события, rollback snapshots и транзакция полного будущего хода сюда ещё
не включены. Тесты подтверждают восстановление после сбоя процесса; испытания
отключения питания и настоящее исполнение desktop-пакета не проводились.

На первом этапе движок владеет новым расчётным разделом; адаптер обновляет
существующие представления карты и статов из него. Запрещено поддерживать два
независимо изменяемых источника экономики. Существующие LLM-последствия для
расчётных полей перехватывать на общем пути применения, а не только в UI.
Старые партии должны сохранять прежний режим до явной безопасной миграции.

## Sign in with ChatGPT: результат проверки

На 2026-10-24 следующие предоставленные пользователем официальные URL
возвращают через прокси среды `Tunnel connection failed: 403 Forbidden`:

`developers.openai.com` добавлен в custom allowed domains черновика среды;
публикация/применение ещё не подтверждены. Другие сетевые настройки сохранены.
Документы не прочитаны: наличие функции, доступ Plus, scopes, модели, endpoint,
регистрация и лимиты **не подтверждены**. Наличие Responses-клиента в игре
не подтверждает поддержку подписочной авторизации. Не реализовывать guessed OAuth.

После применения сетевых настроек повторить чтение этих документов и записать
проверенные ограничения с датой. Если интеграция доступна, хранить токены в
поддерживаемом защищённом локальном хранилище и реализовать PKCE/state,
отзыв/истечение/выход, разрешённые scopes и лимиты. Не переносить OAuth-токены
в существующее небезопасное хранение API-ключей без отдельного анализа.
Если интеграция недоступна, программный режим остаётся полноценной базой.

## Лицензии и ресурсы

Сохраняем LICENSE и атрибуции основного проекта. Код второго проекта не перенесён.

нужна отдельная проверка, AGPL не выдаёт разрешения на эти данные.

подложек без проверки условий не выполнять.

## Первый ограниченный участок этапа 1

Исправлен `/api/app-update`: `autoUpdate` вычисляется по локальному процессу
при каждом ответе, включая сбой сети, HTTP-ошибку, повреждённый JSON и кэш.
Раньше холодный offline-ответ был `{}`, а кэш мог удерживать устаревшую возможность.
Регрессионные тесты подменяют только удалённый запрос и проверяют реальный HTTP API,
поэтому не требуют GitHub. Это улучшение устойчивости существующего приложения,
**не** реализация автономного игрового хода.
