# Население, сети и альтернативы версии 0.3.0

`simulation/migration.js` хранит optional `strategy.migration` (version 1):
население/ожидающие/беженцы, места/квоты/эскроу-фонд, сроки мер, bounded flows.
Единицы населения — целые люди; денег — целые млн €. Месячное распределение
использует общий snapshot; приход и расход населения равны. Интеграция ранее
прибывших потребляет целевой фонд, освобождает места и меняет выпуск/занятость.
Убывающая страна теряет часть выпуска. Источники и допущения описаны в
[MIGRATION_AND_INTELLIGENCE.md](MIGRATION_AND_INTELLIGENCE.md).

`server/spycraft.js` — прежняя чистая spycraft Open Historia с атрибуцией,
`src/runtime/spycraft.js` сохраняет старый API через реэкспорт. Native adapter
`simulation/intelligence.js` добавляет стоимость, подготовку, оплату содержания,
еженедельные seed/date-keyed проверки, монотонные id, resource-bound foreign
networks и NPC-реакцию на оценки угрозы. Авторитетное состояние — optional
`strategy.spycraft` (version 1). Отдельной изменяемой копии в world.spies нет.
`intelligenceView` скрывает непойманных чужих агентов и тайный статус своих
двойных источников; только эта проекция доступна кабинету/UI. Старый legacy
движок продолжает использовать собственный прежний world contract.

Обе подсистемы включаются для новых партий; старые сохраняют прежние правила
до явной команды migration_enable/spy_enable. Новые данные проверяет общий
validateStrategy; сервер, IndexedDB, экспорт/импорт и crash recovery используют
существующую атомарную фиксацию мира. Даты/RNG не двигаются на паузе.

`simulation/recommendations.js` строит бесплатные программные альтернативы и
preview тем же strategyDecision. LLM может вернуть optional suggestions (до 3),
исключающие общий actions. Каждая альтернатива становится отдельным сообщением
с Proposal на одну revision. Принятие одной атомарно делает остальные stale.
Ни текст рекомендации, ни её предпросмотр не изменяют мир.

Сетевые исправления 0.2.1 сохранены. Настоящий Electron transport проверен на
Windows synthetic proxy/provider в CI 40175492073: direct loopback, отдельный
proxy transport, response.completed без EOF, отказ от partial и доступность
сервера после сбоя. Пользовательский аккаунт/его VPN не проверены.

проверены с synthetic provider, не с пользовательской подпиской. Системный
транспорт Electron net.fetch из 0.1.1 сохраняется.

# Текущее состояние: автономная версия 0.1

`simulationMode: native` выбирает отдельный исполнитель и русский HUD поверх
существующего WorldMap. `rulesVersion: 2` включает `world.strategy`; версия 1
сохраняет календарный контракт старых контрольных партий. Legacy-партии не
мигрируют автоматически. В v2 revision считает дневные шаги и принятые решения;
время при решении на паузе не изменяется.

`strategy.js` — чистые типизированные детерминированные правила. Бюджет,
предел долга, реформы, торговля, санкции, разведка и войны не вызывают LLM.
`geography.js` строит сухопутное соседство из общих рёбер сценарной геометрии.
Контроль и суверенитет хранятся раздельно; результат хода проецируется в прежние
поля карты. Единственный источник экономики — `world.strategy`.

Операции start/decision/advance проходят общий clockCommand. Сервер фиксирует
весь расчёт и метаданные через проверенный journal; IndexedDB — одной readwrite
транзакцией. Результат проверяется до публикации journal. Legacy raw PUT и
обновление расчётных разделов native-партии запрещены на сервере и внутри
IDB-транзакции, включая гонку со старой вкладкой. Метаданные партии редактируемы.

Windows использует отдельный entry `electron/strategy.cjs`, appId и профиль.
Автообновление upstream не выполняется. Локальный сервер слушает только loopback.
Крупные карты загружаются при первом запуске оригинальным загрузчиком и
проверяются SHA-256 самим launcher. FMG поставляется для исходного редактора.
Реальный EXE на Windows не запускался; браузерный интерфейс проверен при
блокировке всех внешних HTTPS-запросов.

`chatgptPlan.js` реализует dynamic_agent_client, стабильный host ID, одноразовые
state/nonce, PKCE S256, loopback callback `/auth/callback`, выданный client_id,
проверку RS256/JWKS/issuer/audience/expiry/nonce/subject и отдельные аккаунты.
Scopes: openid profile email offline_access resource.invoke chatgpt.tokens.use.direct;
resource: https://api.openai.com/v1. Refresh сериализуется и ротируется атомарно,
соблюдается earliest_refresh_at. Выход стирает локальные токены до отзыва и
сообщает о неподтверждённом удалённом отзыве.

Windows защищает весь credential store Electron safeStorage; standalone Node —
файл 0600/каталог 0700. Токены не уходят в браузерное хранилище, игровые сохранения,
журнал ходов или экспорт. OAuth API доступен только по loopback. Windows-сборка
не включает `server/data`, тестовые профили или пользовательские секреты.

Модели читаются из каталога данного аккаунта; только visibility=list и slug.
Запрос к public Responses использует store:false, stream:true и input-массив,
без неподдерживаемых generation parameters. Успех требует response.completed;
failed/incomplete/оборванный поток не выдают частичный ответ за успех. Контекст
содержит свою страну, публичные события и доступные разведотчёты. Ответ — совет,
без доступа на запись к миру. Кнопка отправки явно сообщает расход лимита.
Программные рекомендации работают независимо от входа.

Реальная авторизация/инференс НЕ проверены: auth.openai.com блокируется прокси
403 даже после разрешённого повторного запроса. Протокол проверен изолированными
тестами с RSA-подписанными fixtures; Windows DPAPI в Linux не проверялся.

## Проблемы, определяющие план

1. LLM предлагает события и численные изменения, затем существующие валидаторы
   и `applyEventImpactsToWorld` применяют их. Это не заменяет законов экономики,
   ратификации договоров и ресурсных ограничений. Формальная JSON-схема недостаточна.
2. `countryStats` хранится, но исходные значения могут быть AI-оценками. Нельзя
   преобразовать их в «исторические факты» без происхождения и единиц.
3. `maybeSendIdleDiplomacy` использует `Math.random`, есть процессы вне продвижения
   даты. Для нового режима нужны управляемая случайность и запрет значимых
   изменений мира во время паузы; косметическое движение не равно ходу.
4. Нормализация мира перечисляет поля явно. Просто добавить `world.simulation`
   недостаточно: нужны round-trip тесты всех read/write/export/import путей.
5. Сохранения распределены по assets; атомарная запись отдельного файла не
   доказывает атомарность полного хода. Нужны journal/revision, восстановление
   и проверка частичных отказов до включения расчётного режима.
6. Рабочая сборка/тесты не доказывают качество карты в браузере. Визуальная
   проверка и длинная партия пока не выполнены.

Новые общие чистые модули размещаются в `server/simulation/`: существующая
упаковка поставляет сервер без `src/`, что проверяет `server/serverImports.test.js`.
Клиент импортирует их так же, как другие общие серверные helpers. Модули не
зависят от React, fetch, localStorage или системных часов. Контракты описаны
JSDoc с `@ts-check` и проверяются TypeScript без нового runtime/loader; так
сохраняется совместимость с существующим JS-стеком и Node test runner.
Выделять модули по мере реализации: state/commands, time/PRNG, economy,
diplomacy, politics, intelligence, military, characters, autonomousAI.
Не создавать заранее десятки пустых модулей.

Предполагаемый заголовок сохранения: `schemaVersion`, `rulesVersion`, `revision`,
`scenarioId`, `date`, `rngState`. Типы стран, договоров, действий и источников
получают явные единицы и ID. `rngState` содержит текущее состояние PRNG, не только
первоначальный seed. Миграции идут последовательно и не перезаписывают оригинал
до успешной валидации. Снимок старой партии остаётся восстановимым.

Первый реализованный контракт — `world.simulation` в `server/simulation/state.js`:
`schemaVersion: 1`, `rulesVersion: 1`, `scenarioId`, `date`, `revision`,
`rng: { algorithm: 'mulberry32-v1', seed, state, draws }`.
Версия 1 заголовка принимает канонические даты нашей эры 0001–9999;
старые сценарии до н. э. остаются в прежнем режиме и не изменяются.
Календарная арифметика используется через общий gameDates; её реализация
перенесена в поставляемый `server/` без изменений, клиентский импорт сохранён.
Отсутствие поля сохраняет legacy-формат; явное создание заголовка не включает
новый исполняющий движок и не меняет существующий UI. При чистом календарном
шаге согласование с `game.gameDate` проверяет `advanceSimulationClock`;
обычная запись header через прежний API сама по себе не выполняет игровой ход.
Валидатор отклоняет неизвестные версии/поля, повреждённые значения и несовместимый
PRNG; миграций между расчётными версиями пока нет, первая поддерживаемая — 1.
Проверка не «лечит» данные значениями по умолчанию и не создаёт seed автоматически.

`drawRandom` — чистая функция: возвращает значение [0, 1) и новый checkpoint,
не меняя вход. Используется Mulberry32 с фиксированной арифметикой uint32;
проверяется согласованность seed/state/draws и переполнение счётчика.
Нормализатор клиента сохраняет отдельную копию checkpoint; серверный и веб-backend
проверяют входящие runtime-записи и импорты до изменения данных партии.
Проверка вложенных rollback snapshots, общая миграция всех assets и транзакция
полного игрового хода остаются отдельной работой, не следуют из этого контракта.

`server/simulation/time.js` реализует чистые `advanceSimulationDay`,
`advanceSimulation` (day/week/month) и `advanceSimulationClock` (пара game/world).
Месяц — тот же день следующего календарного месяца с ограничением последним
днём, например 2016-01-31 → 2016-02-29. Все интервалы проходят общий дневной шаг.
`revision` считает обработанные дни, а не запросы или записи сохранения:
неделя эквивалентна семи дневным шагам. На этом участке дни ещё не выполняют
экономику/NPC и не расходуют RNG; checkpoint сохраняется.

Адаптер отклоняет legacy-партию и расхождение двух дат, возвращает независимые
копии game/world с одинаковой новой датой и числом прошедших дней. Он не меняет
legacy round, не пишет файлы/IndexedDB, не включает новый режим UI и не является
транзакцией сохранения. Переполнение revision и выход за диапазон дат header v1
отклоняются без изменения входного состояния. Локальная и веб-запись результата
с контролем revision описаны ниже; UI и решения NPC следуют отдельно.

### Локальная фиксация календарного шага

`POST /api/games/:gameId/simulation/advance` принимает только
`{ "step": "day" | "week" | "month", "expectedRevision": integer }`.
`advanceGameClock` в libraryStore обращается к конкретной партии, независимо
от выбранной в интерфейсе. Клиент не присылает замену мира: результат вычисляет
сервер. Ответ содержит gameId, game, world и days. Устаревшая revision даёт 409,
некорректная команда/legacy-партия — 400, отсутствующая партия — 404,
неожиданная ошибка хранения — 500. UI пока не вызывает эту операцию.

`server/simulation/clockStore.js` синхронно выполняет сравнение revision и
фиксацию в одном процессе сервера. До изменения файлов публикуется
`.simulation-clock-journal.json`: версия envelope, сериализованный результат
и SHA-256 payload. Он содержит game, world и метаданные партии; updatedAt
обновляется вместе с ними, чтобы восстановленный ход менял cacheToken.
Затем три файла по очереди заменяются через временные файлы, fsync и rename;
после завершения journal удаляется. На поддерживаемых платформах синхронизируется
также каталог. Windows использует atomic rename без directory fsync.

Опубликованный journal означает намерение завершить ход. После прерывания
восстановление повторно записывает весь результат и удаляет journal; повторение
восстановления безопасно. Оно встроено в чтение/запись верхнеуровневых JSON-файлов
партии и getGameDetails. Ошибка разбора, неподдерживаемая версия или несовпадение
SHA-256 не приводят к сбросу данных: journal остаётся, чтение пары завершается
ошибкой до её выдачи. Экспорт после успешного восстановления видит одну дату.

Сбой после публикации journal может вернуть 500, хотя ход уже зафиксирован либо
будет завершён восстановлением. Клиент должен перечитать указанную партию и её
revision; повтор исходного запроса получает 409 и не выполняет ход дважды.
Это проверено завершением дочернего процесса после каждого из четырёх rename.
Отдельно проверены отказ до публикации journal и восстановление штатным чтением
libraryStore в новом процессе.

Граница гарантии — календарная операция локального сервера, один процесс на
каталог данных. Межпроцессной блокировки нет. Старые raw PUT/update API не
получили CAS; новый UI должен использовать специальную операцию, а переключение
режима должно исключить конкурирующие legacy-писатели. NPC, события,
rollback snapshots и транзакция полного будущего хода сюда ещё
не включены. Тесты подтверждают восстановление после сбоя процесса; испытания
отключения питания и настоящее исполнение desktop-пакета не проводились.

### Веб-фиксация календарного шага

Общий модуль `server/simulation/clockCommand.js` проверяет запрос, идентичность
партии/сценария, даты и revision; локальный и веб-backend используют одинаковые
правила и ошибки. Модуль не импортирует файловую систему и доступен в Vite-сборке.
Прежний импорт ClockRequestError из clockStore сохранён через реэкспорт.

Веб-обработчик поддерживает тот же POST `/api/games/:gameId/simulation/advance`.
`idbUpdatePair` в `src/runtime/web/idb.js` открывает одну readwrite-транзакцию
по games и gameMeta: читает актуальную запись, проверяет revision, вычисляет
следующий шаг и сохраняет всю партию с проекцией каталога. Даты, метаданные,
cacheToken и индекс меняются вместе. Посторонние разделы партии (события,
снимки, обложки) сохраняются. Активная партия в манифесте не меняется.

IndexedDB сериализует пересекающиеся readwrite-транзакции между вкладками;
проверка revision выполняется внутри этой области, поэтому два запроса с одной
revision дают один успех и один 409. Общая внутривкладочная serializeWrite
сохраняется для совместимости с текущими писателями. Она сама по себе не
заменяет межвкладочную транзакцию. Legacy raw PUT пока не приобрёл CAS и
по-прежнему должен быть исключён из расчётного режима при подключении UI.

Транзакционная обвязка разрешает Promise только на complete, отклоняет после
abort и сохраняет исходную прикладную ошибку. Синхронная ошибка callback также
вызывает abort. Если первая put уже поставлена в очередь, отказ второй записи
откатывает обе. Успех отдельных IDBRequest ещё не означает фиксацию транзакции.
Внутри update/project используются только синхронные вычисления; ожидать сеть
или таймеры внутри активной транзакции нельзя.

Настоящая IndexedDB проверяется тестом `simulationClock.browser.test.js` через
две вкладки Chromium с отдельными соединениями, ошибку записи индекса,
принудительный abort после успешных put-запросов и перезагрузку страницы.
Подменяется только генерируемый сценарный контент, хранилище и обработчики —
реальные модули. Это не визуальная приёмка игры и не тест Android WebView.

На первом этапе движок владеет новым расчётным разделом; адаптер обновляет
существующие представления карты и статов из него. Запрещено поддерживать два
независимо изменяемых источника экономики. Существующие LLM-последствия для
расчётных полей перехватывать на общем пути применения, а не только в UI.
Старые партии должны сохранять прежний режим до явной безопасной миграции.
